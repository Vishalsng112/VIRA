    VIRA Link Roadmap¶

    Goal: make VIRA Link a mature, privacy-first device companion that collects useful behavioural and device context locally, works offline, and gives the VIRA server enough structured data to power useful agents later.

    Legend: Done · Now · Next · Later

    1. Product principles¶

    1. Local first. Capture writes to the device outbox before any network call.
    2. Explicit consent. Every sensitive signal has its own switch and OS permission. App usage is opt-in at the OS level through Usage Access.
    3. Minimum necessary data. Prefer aggregates and metadata over raw content. Never collect keystrokes, message bodies, passwords or clipboard content by default.
    4. Server is authoritative. Device identity, credentials, scopes and event policy come from the VIRA server.
    5. Modular collectors. A feature should be addable or removable without touching sync, storage or the UI shell.
    6. Explainable insights. Every summary must be traceable to events the user can inspect, export or delete.
    7. Graceful degradation. Unsupported platforms report unavailable, not fake data.

    2. What is useful to capture¶

    3. Use cases this unlocks¶

    1. Digital wellbeing coach — daily screen time, top apps, late-night usage, category balance and weekly trends.
    2. Student focus coach — compare study/education time with social and games, suggest focus blocks and exam-week limits.
    3. Context-aware assistant — “you usually study at 7 pm; should I enable focus mode?” or “you have been on social apps for 45 minutes”.
    4. Daily and weekly reviews — the agent summarises what happened, what changed and what to try next.
    5. Habit and pattern detection — streaks, first-app-of-the-day, doom-scroll sessions, late-night screen time, weekend vs weekday patterns.
    6. Personal recommendations — learning app suggestions, break reminders, app limits, sleep hygiene, fitness routines.
    7. Task automation triggers — start a focus session when a study app opens, pause notifications during deep work, queue a review after a long session.
    8. Device fleet health — low battery, high CPU, storage pressure, stale devices, unusual activity.
    9. Security and anomaly detection — unexpected app usage bursts, revoked credential detection, unusual sync patterns.
    10. Privacy-preserving local insights — summaries on-device before sending raw events, with redaction and aggregation.

    4. Current architecture¶

    collectors -> CaptureService -> OutboxStore -> SyncService -> VIRA API
                    |                              |
                    +-> UsageLedger (local)        +-> heartbeat
                    +-> Settings (consent)
    • Collector contract: id, title, description, capability, event type, interval, default-enabled, optional access request.
    • CollectorResult reports available, unavailable, permission_denied or degraded plus a human-readable message.
    • CaptureService schedules collectors and writes events to the outbox.
    • UsageLedger keeps a 30-day local daily rollup for offline Insights.
    • SyncService batches events, retries with backoff and heartbeats capability status.
    • Insights is a module in the shell, not hard-coded navigation.

    Event naming¶

    device.telemetry.state          device/app identity and status

    6b. Deployment / external work¶

    These items cannot be finished inside this repository alone:

    • Store-signed APK/AAB/IPA (signing keys, Play/App Store accounts).
    • Health Connect, Google Play Services location and vendor health APIs.
    • GNOME extension activation on Wayland (requires a user session restart).
    • OS notification scheduling and background workers on each platform.

    The code surfaces these limitations in the UI instead of silently pretending the signal is available.

    7. Privacy and consent requirements¶

    • Every collector must be independently disableable.
    • Sensitive collectors default to off unless the OS permission itself is the explicit consent (current Android app usage flow).
    • The UI must show what is captured, when it last ran and why it is unavailable.
    • Users must be able to clear local history and delete server data.
    • Never collect message bodies, passwords, keystrokes or clipboard content by default.
    • Prefer device.* for durable aggregates and sensor.*/telemetry for high-volume raw signals.
    • Include retention class and capability status in the event/heartbeat contract.

    8. Platform capability matrix¶

    Capability Android iOS Linux Windows macOS Web
    Device/app status Yes Yes Yes Yes Yes Yes
    Network Yes Yes Yes Yes Yes Limited
    Hardware metrics Limited No Yes Partial Partial (storage) No
    App usage Yes (Usage Access) No (sandbox) Yes (active window) Yes (foreground window) Yes (frontmost app) No
    Screen on/off Yes No Partial Partial No Limited
    Battery Yes No Yes Partial No API-dependent
    Focus / idle Yes No Yes Yes Yes No
    Notifications In-app only In-app only In-app only In-app only In-app only In-app only
    Crash diagnostics Opt-in Opt-in Opt-in Opt-in Opt-in Opt-in
    Calendar Opt-in later Opt-in later Opt-in later Opt-in later Opt-in later No
    Location Opt-in later Opt-in later Opt-in later Opt-in later Opt-in later Opt-in later

    Platform limitations are product constraints, not bugs. The client must report them honestly through permission_denied and unavailable states.

    Every available row above is represented by a toggle on Overview. Android Focus/idle is implemented through UsageStats; Linux screen on/off remains partial and is represented by the desktop Focus & idle signal. Notifications and crash diagnostics have app-feature toggles. Calendar and location remain future opt-ins.

    9. Success metrics¶

    • ≥ 95% of captured events eventually acknowledged by the server
    • Queue survives app restart and offline periods without data loss
    • App usage capture adds < 2% battery overhead per hour
    • Insights load from local storage in < 300 ms
    • Every collector has a clear consent state and capability report
    • User can export and delete all local data in one flow
    • No sensitive content is read without an explicit opt-in

    10. How to add a collector¶

    1. Create lib/services/capture/collectors/<name>_collector.dart.
    2. Implement Collector with a unique id, capability, event type and interval.
    3. Return CollectorResult.available/... and set canRequestAccess if an OS permission is needed.
    4. Add it to CaptureService._collectors.
    5. Add category/summary logic to the relevant ledger or page if needed.
    6. Write a unit test with a fake platform probe/source.
    7. Document the new event in this roadmap and in client/README.md.

    Removing a collector is the reverse: remove it from CaptureService, delete the file, and remove its capability from the UI.
